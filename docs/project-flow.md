## 1. 项目概述

### 1.1 项目定位

面向正在求职、实习或初入职场的青年，提供关键文书处理服务：

`上传文档 -> 识别内容 -> 分析问题 -> 生成结果 -> 用户确认 -> 导出文件`

项目不试图一次性解决所有文书问题，而是围绕青年的阶段性需求逐步扩展。

### 1.2 目标用户

| 用户类型 | 典型场景 | 主要需求 |
| --- | --- | --- |
| 在校学生 | 实习申请、助学金申请、活动申请 | 表达规范、内容完整、格式正确 |
| 应届毕业生 | 求职、面试、签约 | 简历匹配岗位、识别合同风险 |
| 实习生 | 入职、报销、日常申请 | 降低文档处理成本、快速完成报销 |
| 初入职场青年 | 租房、兼职、离职、请假 | 看懂合同、规范书面表达 |

### 1.3 核心价值

- 降低文书处理门槛。
- 将复杂文档转成通俗、可执行的结果。
- 减少遗漏、格式错误和常见风险。
- 把重复工作交给 Agent，把最终判断权留给用户。

### 1.4 第一版不做的事情

- 不提供正式法律意见。
- 不替用户编造简历、经历或申请事实。
- 不自动替用户签署、提交或对外发送文件。
- 不承诺岗位匹配结果、录取结果或报销结果。
- 不在 MVP 阶段同时开发四个完整模块。

## 2. 用户旅程

```mermaid
flowchart LR
    A[进入网站] --> B[选择任务]
    B --> C[上传文件或输入内容]
    C --> D[系统解析]
    D --> E[用户确认关键信息]
    E --> F[Agent 分析或改写]
    F --> G[展示结果与依据]
    G --> H{用户是否满意}
    H -- 否 --> I[补充信息或调整要求]
    I --> F
    H -- 是 --> J[导出 Word 或 Excel]
    J --> K[收集反馈]
```

用户旅程分为三个阶段：

1. 求职阶段：优化简历、生成申请材料。
2. 签约阶段：审阅合同、识别风险、生成修改提示。
3. 在岗阶段：识别票据、整理开销、导出报销表。

当前 MVP 已实现 Markdown、JSON 和票据 CSV 导出；流程图中的 Word、Excel 通用导出属于后续目标，不代表当前已经完成。

## 3. 产品模块

### 3.1 模块总览

| 模块 | 所属阶段 | 核心任务 | 主要输出 | 开发优先级 |
| --- | --- | --- | --- | --- |
| 简历优化 | 求职 | 提取经历、匹配岗位、优化表达 | 优化简历、匹配分析、面试建议 | P0 |
| 申请书函润色 | 求职与职场 | 规范语言和格式 | 润色后的申请信、辞职信、请假条 | P0 |
| 合同审阅 | 签约 | 识别权责与风险条款 | 通俗摘要、风险清单、修改提示 | P1 |
| 票据开销整理 | 在岗 | OCR 识别、分类、统计 | 收支表、报销清单、Excel 文件 | P2 |

### 3.2 模块一：简历优化

**输入**

- PDF、DOCX 简历
- 目标岗位描述
- 可选补充信息，例如项目成果、实习数据、求职方向

**处理流程**

1. 解析简历文件。
2. 提取个人资料、教育经历、项目经历、实习经历和技能。
3. 解析目标岗位要求。
4. 对经历与岗位要求进行匹配。
5. 查找表达模糊、缺少量化、重点不清的问题。
6. 在不改变事实的前提下重写。
7. 输出优化后正文和修改说明。

**输出**

- 结构化个人档案
- 岗位匹配分析
- 逐段修改建议
- 优化后的简历
- 面试准备问题
- DOCX 导出文件

**约束**

- 不编造学历、项目、数据或证书。
- 无法确认的信息必须标记为“待用户补充”。
- 匹配分数必须说明评分维度。

### 3.3 模块二：申请书函润色

**适用范围**

- 实习申请
- 求职信
- 助学金申请
- 活动申请
- 请假条
- 辞职信
- 其他个人书面材料

**处理流程**

1. 接收用户初稿。
2. 识别文书用途、对象和语气。
3. 检查结构、表达和格式。
4. 标记空泛、重复和不自然的内容。
5. 在保留事实的前提下润色。
6. 提供修改前与修改后的对照。

**约束**

- 不进行法律或财务风险审查。
- 不添加用户未提供的事实。
- 不替用户表达未经确认的承诺或立场。

### 3.4 模块三：合同审阅

**适用范围**

- 租房合同
- 兼职协议
- 实习协议
- 劳动合同
- 离职协议
- 其他青年常见协议

**处理流程**

1. 上传 PDF、Word 或合同照片。
2. OCR 和文档解析。
3. 按章节和条款切分文本。
4. 识别金额、期限、违约责任、解除条件、押金、竞业限制等要素。
5. 将风险分为低、中、高三级。
6. 用通俗语言解释条款。
7. 提供谈判或修改提示。
8. 引导用户对重大风险咨询律师或专业机构。

**输出**

- 合同基本信息表
- 权责摘要
- 风险条款清单
- 修改建议
- 需要向对方确认的问题

**边界**

- 明确声明结果仅用于辅助理解，不构成法律意见。
- 法律风险应尽量引用可核验依据，不能凭空生成法条。
- 涉及重大金额、人身权益、劳动权益时，必须提示人工复核。

### 3.5 模块四：票据开销整理

**输入**

- 发票照片
- 小票照片
- PDF 票据
- 多张票据组成的批次

**处理流程**

1. 图片预处理和 OCR。
2. 提取票据类型、商家、日期、金额、税额和报销类别。
3. 校验金额、日期和重复票据。
4. 对无法识别的字段进行人工确认。
5. 汇总统计。
6. 导出 Excel。

**输出**

- 票据明细表
- 分类汇总
- 异常和重复提示
- Excel 报销清单

**约束**

- 提取结果必须由用户确认。
- 金额计算采用程序计算，不只依赖模型文本输出。
- 不代替财务审核或税务处理。

## 4. 总体技术架构

### 4.1 架构原则

四个模块共享应用底座，但业务工作流相互独立。前期采用“任务路由 + 单一专用工作流”，不直接搭建复杂多 Agent 系统。

### 4.2 分层架构

```mermaid
flowchart TB
    UI[网页前端] --> API[后端 API]
    API --> AUTH[用户与权限]
    API --> TASK[任务管理器]
    TASK --> ROUTER[任务路由器]
    ROUTER --> RESUME[简历工作流]
    ROUTER --> LETTER[申请书工作流]
    ROUTER --> CONTRACT[合同工作流]
    ROUTER --> RECEIPT[票据工作流]
    RESUME --> PARSE[文档解析服务]
    LETTER --> PARSE
    CONTRACT --> OCR[OCR 服务]
    RECEIPT --> OCR
    PARSE --> MODEL[模型调用层]
    OCR --> MODEL
    MODEL --> VALIDATE[结构化校验]
    VALIDATE --> RESULT[结果与导出]
    RESULT --> STORE[文件与任务存储]
    STORE --> EVAL[评测与日志]
```

### 4.3 共享能力

- 用户登录和权限控制
- 文件上传、存储和删除
- PDF、DOCX、图片解析
- OCR
- 模型调用和超时重试
- 任务状态管理
- 结构化输出校验
- Word 和 Excel 导出
- 执行日志、成本统计和评测

### 4.4 模块专属能力

| 模块 | 专属规则 | 专属工具 |
| --- | --- | --- |
| 简历优化 | 岗位匹配、经历提取、事实约束 | 简历解析、DOCX 导出 |
| 申请书函 | 文体、语气、格式、事实约束 | 文本对照、DOCX 导出 |
| 合同审阅 | 条款切分、风险分类、法律依据 | OCR、条款定位、风险规则库 |
| 票据整理 | 金额校验、分类统计、去重 | OCR、表格校验、Excel 导出 |

## 5. Agent 设计

### 5.1 Agent 角色

MVP 阶段只设一个主入口：

> 文档任务 Agent：判断任务类型，调用对应工作流，收集必要信息，生成可确认的结果。

### 5.2 运行步骤

```mermaid
sequenceDiagram
    participant U as 用户
    participant A as Agent
    participant T as 工具层
    participant M as 模型层
    participant S as 存储层

    U->>A: 上传文件并提出目标
    A->>T: 解析文件
    T->>S: 保存原始文件和解析结果
    T-->>A: 返回结构化内容
    A->>U: 请求确认缺失或不确定信息
    U-->>A: 补充信息
    A->>M: 调用对应模块策略
    M-->>A: 返回结构化结果
    A->>T: 校验并生成导出文件
    T-->>U: 返回结果和下载链接
    U->>A: 提交反馈
    A->>S: 保存反馈和评测数据
```

### 5.3 Agent 必须具备的能力

- 任务分类
- 文件解析
- 缺失信息追问
- 模块工作流选择
- 结构化输出
- 事实一致性检查
- 风险等级判断
- 文件导出
- 错误恢复
- 结果来源说明

### 5.4 Agent 禁止行为

- 不确认事实就自动补全
- 把模型猜测当作确定结果
- 在无法识别时静默继续
- 将法律辅助结果包装成正式法律意见
- 未经用户确认自动对外提交文档

## 10. 评测体系

### 10.1 通用指标

| 指标 | 说明 |
| --- | --- |
| 解析成功率 | 能否成功读取文件并提取正文 |
| 任务完成率 | 用户是否获得可用结果 |
| 事实一致性 | 是否出现原文没有的信息 |
| 结构化准确率 | 字段是否正确归类和抽取 |
| 用户采纳率 | 用户是否采用建议或导出结果 |
| 平均耗时 | 从上传到结果完成的耗时 |
| 单任务成本 | 模型、OCR、存储等综合成本 |
| 失败恢复率 | 错误后是否能重试或补充信息 |

### 10.2 模块专属指标

| 模块 | 重点指标 |
| --- | --- |
| 简历优化 | 经历提取准确率、岗位匹配解释性、事实编造率 |
| 申请书函 | 事实保持率、语气符合度、格式规范度 |
| 合同审阅 | 风险召回率、误报率、条款定位准确率 |
| 票据整理 | 字段识别准确率、金额正确率、重复票据识别率 |

### 10.3 评测流程

1. 选择固定脱敏样本。
2. 保存人工基线结果。
3. 每次修改后运行同一批样本。
4. 对比准确率、成本、耗时和失败类型。
5. 人工复核高风险输出。
6. 通过后再上线。

## 11. 风险与应对

| 风险 | 影响 | 应对 |
| --- | --- | --- |
| 同时开发四个模块 | 进度失控、质量不稳定 | 先做求职文书 MVP |
| 模型编造经历 | 用户求职风险 | 事实字段锁定、生成后校验 |
| 合同审查错误 | 法律和经济损失 | 风险分级、来源依据、人工复核提示 |
| OCR 识别错误 | 报销金额错误 | 程序校验、低置信度确认、重复检测 |
| 个人文件泄露 | 隐私和信任问题 | 加密、最小权限、删除机制 |
| 成本过高 | 无法持续运营 | 限制文件大小、缓存解析、记录单任务成本 |
| 用户不愿付费 | 无法商业化 | 先验证重复使用和真实付费意愿 |
| 法律边界不清 | 合规风险 | 明确辅助定位、保留免责声明、重大风险转人工 |

| 3 | 隐私与文件生命周期 | 第 5 周 | 完成删除、保存期限、日志脱敏、访问控制 | 隐私说明、数据生命周期、删除验证 | 通过决策门 D |
| 4 | 封闭内测 | 第 6 至 7 周 | 邀请 20 至 50 名用户独立完成任务 | 内测报告、Top 10 问题、留存和再次使用数据 | 完成率、重复使用和稳定性达到门槛 |
| 5 | 单模块付费试验 | 第 8 周以后 | 只选择一个成熟模块验证真实付款 | 价格页或付款方式、订单记录、单位成本 | 通过决策门 E 和 F |
| 6 | 小规模扩展 | 付费试验通过后 | 扩展用户、存储和运维能力 | 稳定部署、监控、客服和回滚流程 | 成本、错误率和获客仍然可控 |
| 7 | 多 Agent 评估 | 单 Agent 稳定后 | 只在职责边界清晰时拆分 Agent | 分工方案、评测对比和回滚路径 | 多 Agent 的收益能够量化 |

### 13.2 最近两个阶段的具体任务

**第 1 阶段：真实样本验收**

1. 每个任务类型准备 5 份脱敏文档，共 20 份。
2. 为每份文档填写人工基线，包括事实、风险和预期输出。
3. 通过命令行和 Web 工作台各运行一轮。
4. 记录解析成功、任务路由、关键发现、事实编造、耗时和人工修改量。
5. 把失败分成解析、路由、规则、模型、界面和数据格式六类。
6. 输出一份真实样本评测报告，不急着开发新功能。

**第 2 阶段：基线与 v0.3**

1. 只修复评测中出现频率最高且影响最大的问题。
2. 把真实样本加入回归集，保留旧评测防止退化。
3. 将本地标准库 Web 服务拆成正式 API，并补充任务状态和文件生命周期。
4. 增加结构化错误、耗时和单任务成本记录。
5. 模型调用仍然保持可选，在线模型失败不能破坏本地规则模式。
6. 再次运行全部单元测试、历史评测和真实样本评测。

### 13.3 锁定的协作方式

- 当前保持“一个主 Agent + 四条专用工作流”，不提前拆多 Agent。
- 一个阶段只设一个主要目标，未通过决策门不并行开发下一个商业模块。
- 高风险结果始终保留人工复核，不自动代替用户提交。
- 新功能必须对应真实样本中的问题，不能只因为技术上容易实现就加入。
- 任何线上模型、支付和云服务都必须经过成本与隐私评估。

## 14. 项目完成定义

### 当前工程 MVP

状态：已完成。

- 用户可以粘贴文本或上传基础格式文档。
- Agent 可以自动识别四类任务并调用专用工作流。
- 结果包含结构化发现、说明和人工复核提示。
- 用户可以下载 Markdown、JSON 和票据 CSV。
- 本地 Web 工作台不需要模型 API Key 即可运行。
- 核心规则有单元测试和 JSONL 离线评测。

### 可进入内测

- 用户可以确认或补充关键信息。
- 系统可以记录错误、耗时和单任务成本。
- 用户可以删除自己的文件。
- 20 个以上真实样本通过测试。
- 严重事实错误为零或接近零。
- 主要失败情况有恢复路径。
- 隐私和删除流程可用。

### 可考虑商业化

- 有稳定的重复使用需求。
- 有清晰的目标付费人群。
- 有可接受的单任务成本。
- 有明确的责任边界。
- 有可重复的获客渠道。

## 15. 最终流程摘要

```text
工程 MVP 已完成
  -> 真实样本验收
  -> 基线修复与 v0.3
  -> 隐私与文件生命周期
  -> 封闭内测
  -> 单模块付费试验
  -> 小规模扩展
  -> 单 Agent 稳定后再评估多 Agent
```

核心原则：

> 先解决一个真实问题，再增加模块；先验证结果质量，再讨论商业化。

### 16.3 现在明确不使用

- 不提前使用多 Agent 编排。
- 不把单体项目拆成微服务。
- 不使用 Kubernetes。
- 不先做原生移动 App，继续使用响应式 Web。
- 不为了技术流行度引入 React、Vue 或大型前端框架。
- 不先做订阅、优惠券、复杂订单和自动续费。
- 不先建设向量数据库、大型知识库或复杂工作流引擎。
- 不把模型作为唯一判断来源，金额和结构化字段仍由程序校验。

### 16.4 技术引入原则

1. 每项技术必须解决当前阶段已经出现的问题。
2. 优先使用标准库、单机组件和托管服务，降低 One Person Company 的维护成本。
3. 本地规则和离线评测必须保留，不能因为接入在线模型而失效。
4. 个人文档默认不进入云服务，确需上传时必须说明用途、保存时间和删除方式。
5. 数据量、并发、成本或客户需求没有达到门槛时，不提前扩容。
